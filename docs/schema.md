# Schema reference

Authoritative definitions are the JSON Schema files in `schema/`. They are
standards-compliant, so any off-the-shelf validator works. `tools/ci_lib.py`
ships a dependency-free validator covering the keywords used here, so a cloned
instance can be checked with nothing installed.

See [ADR 002](adr/002-schema-shape.md) for what is locked and why.

## File types

| File | Schema | Layer |
|---|---|---|
| `vendors/<slug>.md` | `vendor.schema.json` | Descriptive |
| `signals/sig-<date>-<vendor>-<nn>.md` | `signal.schema.json` | Descriptive |
| `assessments/<slug>.md` | `assessment.schema.json` | Interpretive |
| `product/<name>.md` | `product.schema.json` | Reference |
| `tiers.yaml` | `tiers.schema.json` | Governance |
| `config.yaml` | `config.schema.json` | Governance |
| `profiles/<name>.yaml` | `profile.schema.json` | Framework |

## Organisation context

`config.yaml` carries a required `organisation` block: who you are, as distinct
from what vocabulary you use.

The distinction matters and is easy to blur. `organisation.industry` is free text
describing your company. `profile` names a tier and lane **vocabulary**. One is
identity, the other is the set of words this instance is allowed to use, and a
profile is deliberately reusable by anyone in the same market, including your
competitors.

The block is required because three of its fields do real work:

| Field | Does |
|---|---|
| `size`, `stage` | Calibrate which vendors are plausibly head to head. A twenty-person company and a five-hundred-person company do not have the same tier 1. |
| `icp.must_have_criteria` | The source for every vendor page's "Gaps observed against stated buyer criteria" section, so gaps are recorded against a stable list rather than whatever the writer remembered. |
| `competes_with_platforms` | If true, the validator expects at least one `platform_native` vendor. Claiming bundled capability shows up in your deals while tracking none of it is a coverage gap. |

It also has `reviewed` and `reverify_by`, because size and stage go stale and
both change the competitive set.

`/competeseed` interviews for this block. The shipped template deliberately
fails validation until it is filled in.

## Profile resolution

Profiles resolve from the instance's own `profiles/` directory first, then the
framework's. An instance can therefore adapt or replace a shipped vocabulary
without forking the framework, and a file with the same name as a shipped
profile overrides it.

## Identity and naming

- Vendor filename stem must equal `slug`. Signal filename stem must equal `id`.
  Assessment filename stem must equal `vendor`.
- Signal ids are `sig-YYYY-MM-DD-<vendor-slug>-<nn>`, and the date must match the
  `date` field.
- `slug` is permanent. A rename is a new slug plus `status: merged` and
  `merged_into` on the old page, so history stays resolvable.

## Dates, and which is which

Three dates on a vendor page do different jobs, and conflating them is the usual
source of misleading freshness:

| Field | Means |
|---|---|
| `data_as_of` | The intel on this page describes the vendor as at this date |
| `last_reviewed` | A human last checked this page on this date |
| `reverify_by` | After this date, treat the page as unverified |

A signal has `date` (when the observed thing was true, which drives shelf life)
and `filed` (when it entered the repository). Shelf life runs from `date`, not
`filed`, so a backfilled claim is correctly old the moment it lands.

## The frontmatter subset

Frontmatter must stay inside a constrained YAML subset: scalars, flow and block
sequences, nested mappings, sequences of mappings, and `|` or `>` blocks. Tab
indentation is rejected.

The constraint is deliberate. It keeps every instance file uniform, and it is
what makes dependency-free validation possible. When PyYAML happens to be
installed, `ci_lib` compares its strict parser against PyYAML and fails if they
disagree, which catches frontmatter drifting outside the subset before it reaches
anybody else.

## Generated files

`index.json` is generated by `tools/build_index.py` and committed, so consumers
read it without running anything. CI fails if it is stale.

Read it first. It carries every vendor's tier, lanes, flags, dates, freshness,
signal counts, supersession and conflict state, plus an `attention` block listing
overdue vendors, missing assessments, open contradictions and stale product
references. Most questions are answerable from it alone, at a fraction of the
cost of opening every file.
